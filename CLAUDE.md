# ASK — project instructions

This file defines the scope of this project. It applies only to this folder.

## Isolation (read first)

ASK is a standalone app. Treat it as the only project in existence for the purposes of this folder.

- Source of truth is this folder only: the code under `src/`, plus `README.md`, `ARCHITECTURE.md`, `PRD.md`, and `docs/`.
- Do not carry over logic, conventions, architecture, naming, dependencies, config, credentials, or assumptions from any other app, repo, or earlier Claude session. If something seems to come from elsewhere, it does not apply here.
- Do not read, edit, import from, or run commands in folders outside this one (parent directory, sibling projects, other apps in Downloads).
- Do not reuse other projects' memory, MCP connections, deployments, or accounts (Vercel, Figma, Supabase, etc.) for ASK unless the user names the target in this project's chat.
- When a decision needs context this folder does not contain, ask the user. Do not fill the gap from another project.

## What this project is

Local-first React Native app on Expo Router (`expo ~57`, `react-native 0.86`, TypeScript). Phase 0/1 build: transcript to guarded canonical memory events, plus on-device voice enrollment and verification. See `README.md` and `PRD.md`.

## Voice locket platform (`platform/`)

A second, self-contained subsystem in this repo: company web app, FastAPI backend, local AI worker, and ESP32S3 locket firmware. Plan, decisions, and milestones: `platform/docs/PLAN.md`. Read it before touching anything under `platform/`.

- Layout: `platform/web` (the ASK app frontend: Expo Router, exported to static web files), `platform/api` (FastAPI, Python 3.11 venv), `platform/firmware`, `platform/docs`. Separate dependency trees and env files from the Expo app.
- The Expo app and `platform/` do not import from each other. Root `tsconfig.json` and `metro.config.js` exclude `platform/`; keep it that way.
- Frontend (`platform/web`): the loki1514/ASK-V1 app (Expo Router; one codebase for the phone and the website), wired to `platform/api` on 2026-11-14 (plan: `docs/superpowers/plans/2026-11-14-app-lockets-cloud-pipeline.md`). Screens: Sign in, Today, Ask (search), Activity, You, Recording, Lockets, Team, Account; every button calls the server or the locket. The website is served by `serve.mjs`, which forwards `/api` to the server (same origin). Bluetooth (pairing, Start/Stop, firmware) runs in the phone app via `react-native-ble-plx`, and since 2026-11-15 also in Chrome/Edge on a computer via Web Bluetooth (`src/infrastructure/ble/webBluetoothLink.ts`; parts waiting to upload are kept in IndexedDB, `webFiles.ts`); neither **has ever run** against a locket (tested with fakes only): say so. `EXPO_PUBLIC_API_URL` (platform/web/.env) is read by the phone build only (`base.native.ts`); the website always uses same-origin `/api`. Demo screens and the on-device voice-profile UI were removed. Design system: `src/theme/tokens.ts` (dark, violet `#5B2EFF`, system font). No human figures or portraits anywhere.
- Visitor-facing UI (marketing pages, dashboard text, demo data, alt text) must not name sensors, hardware parts, boards, or third-party products and AI models. Say "audio capture", "local storage", "speech-to-text", "speaker matching" instead. Developer docs and backend code may use real names.
- Every company-owned query is tenant-scoped; cross-tenant object access returns 404. Never trust a company or user ID from the client. Membership comes from invitation or company bootstrap, never from an email domain.
- Never log or return raw audio paths, secrets, or voice embeddings. No fabricated test results or fake success states; demo data is allowed only behind a visible demo-mode label.
- Report what was not run (no Docker, FFmpeg, GPU or ESP32 hardware on this machine unless that changes; PostgreSQL 16 and the Arduino CLI were run from a scratch folder with the owner's permission, see below; the Whisper and speaker-model weights are downloaded under `platform/data/models`, the gated pyannote weights are not).
- Migrations: never rebuild a table with foreign keys enforced (SQLite batch mode cascades deletes into child tables). Prefer plain `op.add_column`; `migrations/env.py` also turns enforcement off and checks for orphans, and `tests/test_migrations.py` seeds child rows and proves they survive. A new migration gets a data-survival test if it alters a table other tables reference.
- Simulated lockets are always labelled (`simulated` on devices and recordings) and refused by production. Never present simulator data as real.
- Security (`platform/docs/SECURITY.md`): the audit log is administrator-only and scrubbed on output; a person cannot change their own role or access; a recording's playback and download are audited; an employee sees a recording because it arrived while the locket was assigned to them (`recordings.assigned_user_id`), never because the locket is theirs now; when real mail is on, an invitation link is never returned to the inviter. Do not weaken these. Items the review left as decisions are in that file, not to be "fixed" silently.
- Firmware (`platform/firmware`) is **compiled but never flashed or run**, and deployment (`platform/deploy`) is **written but unrun**: never describe either as working. The firmware builds for `esp32:esp32:XIAO_ESP32S3` with the real toolchain (Arduino CLI + arduino-esp32 3.3.12, no warnings, 32% of program storage); its pure logic is tested (`platform/firmware/tests/check.ps1`, and `platform/api/tests/test_firmware_interop.py` with a C++ compiler via `ASK_FIRMWARE_CXX`); everything that touches the board has never run. The Compose stack, the proxy and the backup scripts' Docker wrappers have never run (the PostgreSQL side has: see the tests row below). Say so.
- Two sketches share `platform/firmware`: `locket` (continuous 10-second clips, no button) and **`locket_web_upload`** (the button-controlled recorder derived from the user's original ring-buffer recorder: press to start, press to stop, parts uploaded to the ASK server). They speak the same device API and share the logic in `core.cpp` (the copies are kept in step by running `tests/test_core.cpp` against both). The original recorder's speech-to-text, summary and chat-message code is deliberately absent: the device only records, stores and uploads. Do not put keys, tokens or Wi-Fi passwords in any sketch; they are set over serial. **One exception, by the owner's explicit request:** `locket_web_upload/config.h` holds the throwaway test hotspot `ESPTEST` / `12345678` (`ASK_DEFAULT_WIFI_SSID`, `ASK_DEFAULT_WIFI_PASSWORD`) so the locket joins it at power-on with no `wifi` command (`wifi_manager.cpp`, its own task, never blocks recording). It is plain text in source and binary: never print or log the password (a test scans every simulated run and the sources), never extend this to another network, key or token, and say so whenever the firmware is handed on (`platform/docs/SECURITY.md`). A network typed with `wifi` replaces it until `wifi default` or a new build; a new build clears older saved networks. Do not name a sketch file after an Arduino core header (`network.h` collided with the core's `Network.h` on Windows: that is why it is `wifi_manager`). `locket_web_upload` is built for **PSRAM: OPI**, and was run only on a computer against *simulated* hardware (`tests/hostsim`) and against the real API over a local socket, never on a board: say "simulated" every time. Its docs: `platform/firmware/locket_web_upload/README.md` and `platform/docs/WEB_UPLOAD_FIRMWARE.md`.
- Processing (`platform/docs/AI.md`): the stub provider writes placeholder text, never names anyone, and is labelled everywhere (`placeholder` flag, badges, notices, exports); production refuses it. faster-whisper and SpeechBrain have been run on real audio on this machine (CPU, synthetic voices: `tests/real`, `tools/benchmark_pipeline.py`); **pyannote has not** (its model is gated and there is no token), nor has a GPU or any real person's voice. The experimental token-free speaker separator (`ASK_AI_DIARIZER=clustering`) is labelled experimental in the API and dashboard. The speaker threshold is uncalibrated until `calibrate-speakers` is run on real, consented audio: say so, never present matching as identity verification, and never quote an accuracy figure for real people. A wrong name is worse than `Unknown speaker`. Enrollment audio is deleted at once; voice prints are never returned or logged. The dashboard never names models or libraries.
- **Bluetooth locket design (2026-11-14, owner and Nandu):** the locket talks only to the phone over Bluetooth; the phone uploads audio to the server; the server gets the transcript from Google Cloud Speech-to-Text and a summary from Gemini; the phone keeps `transcription.txt` and `summary.txt`; Wi-Fi on the locket is for firmware updates (OTA) only. Pairing needs a six-digit code emailed to the person, derived from the locket's secret (`HMAC(ASK_LOCKET_MASTER_KEY, productId)`, never stored) and a fresh nonce from the locket. Product IDs are permanent (ORM guard + database trigger). People per locket default to 1; only an administrator raises the limit. Design: `docs/superpowers/specs/2026-11-14-ble-locket-cloud-pipeline-design.md`; server plan: `docs/superpowers/plans/2026-11-14-server-lockets-cloud-pipeline.md`. Server side is built and tested (`/api/lockets`, `/api/firmware`, `ASK_AI_PROVIDER=google`); **Google and Gemini were run only against stand-in clients, never for real**, the phone's Bluetooth code is written (app plan) and the Bluetooth firmware is `platform/firmware/locket_ble` (plan: `docs/superpowers/plans/2026-11-15-firmware-locket-ble.md`): it **compiles with no warnings on board packages 3.3.10 and 3.3.12 (about 42% of program storage) but has only been flashed and advertising-checked by the owner, never fully tested**; its `ASK_TEST_PASSKEY` (config.h) is -1 (no fixed PIN) and its `ASK_TEST_NO_PASSKEY` is 1 at the owner's request (2026-11-17): the locket pairs with NO code, so anyone in range can pair, read meetings and push an update; it must be 0 for any locket that leaves the desk (see SECURITY.md); it also has the serial commands `unprovision <ID>` and a reset code for giving a locket a fresh ID, and its pure logic is tested on a computer (`platform/firmware/tests/check_ble.ps1`, shared values with the server and app tests). Say so. The Gemini summary is generative AI at the owner's request; the older rule-built analysis below still exists and stays labelled as rule-built.
- Voice signatures, pitch and the summary (`platform/docs/VOICE_SIGNATURE.md`; code in `platform/api/app/voiceid`, `platform/api/app/insights`, `platform/api/app/services/{signatures,insights}.py`): a **voice signature** (pitch plus 24 numbers of voice colour) is biometric, like a voice print: consent first (checked again before saving), audio deleted at once, the 24 numbers never returned or logged, only the pitch summary shown (to managers in the People list), deleted with consent. Pitch is the first layer: a voice is never compared with a much higher or lower one. It is a coarse fingerprint **calibrated on nothing but two synthetic voices**: say so, never present a match as identity verification, never quote an accuracy figure. `ASK_AI_DIARIZER=pitch` is experimental and opt-in. The summary is built by fixed rules and templates (**no generative AI**; say that, not "AI summary"); it stores speakers by label and looks names up when read. The meaning-based sentence model (`ASK_ANALYSIS_ENGINE`, extra `text`) was installed and its weights fetched once on the owner's go-ahead (`sentence-transformers/all-MiniLM-L6-v2`, in `platform/data/models`) and run offline on CPU; its figures come from a small single-author test set. Weights are never downloaded unless `ASK_AI_TEXT_ALLOW_DOWNLOAD=true`; a new model or another download needs the owner's explicit go-ahead naming file, source and size. The dashboard never names models or libraries for any of it.
- Machine limits found in the last audit: no Docker, FFmpeg, GPU or ESP32 board. The session's permission checker refuses to run programs *downloaded* from the internet; it refused the Arduino CLI and a PostgreSQL server archive until the owner explicitly allowed both (local only, run from the session's scratch folder). That permission was given for those two programs only (official builds, local only): do not work around the checker for anything else. PyPI packages are fine. The portable PostgreSQL used `127.0.0.1:54329` with a throwaway password and was stopped afterwards; the Arduino CLI used its own scratch data folders.

## Architecture rules (from `ARCHITECTURE.md`)

Dependency direction: `UI -> application use cases -> domain interfaces <- infrastructure adapters`.

- `src/domain`: canonical types, function registry, guards, compiler, voice quality, matching, repository contracts.
- `src/application`: use-case orchestration (semantic events, voice enrollment and verification).
- `src/infrastructure`: repositories, protected voice-template storage, ONNX adapter.
- `src/data`: demo fixtures and UI projections. `src/lib`: retrieval adapter.
- UI modules must not import a database, BLE driver, or model runtime directly.
- Parser output is untrusted input to the deterministic guard boundary. No canonical event without transcript evidence.
- The voice engine is a non-biometric prototype until a reviewed ONNX model and calibrated thresholds ship. Never present its result as identity verification.
