# ASK locket firmware: button recorder (`locket_web_upload`)

Firmware for the voice locket: a Seeed Studio **XIAO ESP32S3 Sense**. **Press the button to start recording, press it again to stop.** The recording is saved on the memory card as one or more WAV files and uploaded to the ASK server over Wi-Fi. The server stores it, processes it, and shows it to the right company in the website.

It keeps the recording pipeline of the original single-file recorder (microphone, PSRAM ring, card-writer task, remount recovery) and replaces its cloud steps (speech-to-text, summary, chat message) with the upload. **The device calls none of those services.** Transcription and speaker work happen on the server.

> **Status: compiles with the real ESP32 toolchain; its logic has been run on a computer against simulated hardware and against the real server; it has never been flashed or run on a device.** No board was available where this was written. Read [What was and was not checked](#what-was-and-was-not-checked) before relying on it, and use [../../docs/HARDWARE_ACCEPTANCE_TESTS.md](../../docs/HARDWARE_ACCEPTANCE_TESTS.md) (section 7) on the day you have a board.

Developer documentation: it names parts and libraries. The locket's own pages and the website never do.

## A security note about the original source

The original firmware had a Wi-Fi password, Google API keys and a Telegram bot token in its source. Treat every one of them as **compromised**: change the Wi-Fi password, delete the Google keys in the Google Cloud console, and revoke the Telegram token with BotFather. Nothing like that is in this sketch. A locket holds three secrets, all set over the USB cable and kept in the chip's own storage (never on the card, never printed): the Wi-Fi password, its own per-device credential (from pairing), and the password of its optional maintenance Wi-Fi.

## What changed from the original

| Original recorder | This sketch |
| --- | --- |
| Button: first press starts, second press stops (GPIO2, 50 ms debounce) | **Kept** (`recorder.cpp`, debounce rules in `core.cpp`) |
| 16 kHz, 16-bit, mono WAV; 44-byte header rewritten at the end | **Kept** |
| 32 × 32 KB PSRAM ring, writer task on core 0, 3 zero-write retries, 3 remount attempts, flush every 8 blocks | **Kept** (`sdwriter.cpp`), with the card behind a lock and recovery that no longer assumes unflushed data reached the card |
| Fixed names `record.WAV`, `transcribe.txt`, `summarry.txt`; **the next recording deleted the old ones** | **Gone.** Every part has a unique name; nothing is deleted when a recording starts |
| Google speech-to-text in 10-second chunks, 6 PSRAM buffers, Base64, backlog recovery | **Removed** (server does it) |
| Gemini summary | **Removed** |
| Telegram text and file upload (with `setInsecure()`) | **Removed**, replaced by an upload that checks the server's certificate |
| Recording refused unless Wi-Fi was up | **Recording works offline**; parts wait on the card |
| Web server called from inside the capture loop; always-on access point with a fixed password | The capture task never serves a page. The maintenance Wi-Fi is **off by default**, its password is generated by the locket |
| One file for the whole recording (up to 7000 s) | A long recording becomes **parts** of up to 5 minutes (shorter if the server says so), numbered and tied together |

## How it works

```text
button ─► capture task (core 1) ─► 1 KB read buffer ─► one of 32 PSRAM blocks ─► job queue
                                                                                     │
                                       card-writer task (core 0) ◄──────────────────┘
                                          writes /recording/<part>.wav, flushes, remounts if the card stalls
                                          closes the part, checks it, moves it to /pending
                                                                                     │
                       uploader task (core 0) ◄─────────────────────────────────────┘
                          PUT /pending/<part>.wav to the server, checks the receipt, then deletes
```

* **Capture** only reads the microphone and copies audio into a free block. It never touches the card, the network or a web page. If the card falls 32 seconds behind, the recording stops with an error and what was captured is kept.
* **Parts.** A recording is cut into parts of whole blocks (292 blocks, 299 s, by default; fewer if the server's `maxClipSeconds` or `maxUploadBytes` is smaller). The writer closes one part and opens the next without the capture task noticing. A tail shorter than half a second (the server would refuse it) is not kept, and is logged and counted. All parts of one recording share a session reference and carry a part number, and the website labels them "Part 2".
* **Names.** `<clipId>.<when>.<part>.<sessionRef>.wav`. `clipId` is made from a start-up counter, a random number picked at each start-up and a sequence number, so it is never reused, even after a power cut or a swapped card. The folder is the queue: no index file exists to corrupt. The name is also what makes an upload safe to repeat.
* **Folders.** `/recording` a part being written; `/pending` finished parts waiting to be sent; `/rejected` parts the server will never accept (kept for diagnosis, never deleted); `/untimed` parts recorded before the clock was ever set and from an earlier start-up (kept; see below).
* **One lock for the card.** Every access goes through `storage::Lock`. The writer holds it for one block's write; the uploader reads in 4 KB slices through `storage::Reader`, which steps aside when a remount is wanted and notices when one happened (a file handle from before an unmount must never be used or closed).
* **Uploads while recording** (`ASK_UPLOAD_WHILE_RECORDING`, on by default): finished parts are sent while the next is recorded, but stand down at once if more than half the ring is waiting for the card. Switch it to `0` to upload only after stopping.
* **Time.** If the clock is not set when you press the button, the part is named with seconds since start (`u1234`). Once the network has set the clock, in the same start-up, the exact start time is worked out and used. Parts from an earlier start-up that were never timed are moved to `/untimed` and **not uploaded under a guessed time**.
* **Recovery at start-up.** A part left half written by a power cut is given a correct header for the audio in it and queued (anything under half a second is discarded and logged). Data the card had not flushed is gone; the writer flushes every 8 blocks (about 8 seconds).
* **Pairing is needed to record.** An unpaired locket does not record. If the server later refuses the credential (401), uploads stop, **every file is kept**, new recordings are refused with "pair again", and a recording in progress is never interrupted.

## The button, step by step

**Wiring.** One leg of the push button goes to **D1 (GPIO2)** and the other to **GND**. No resistor is needed: the firmware switches on the pin's own pull-up, so the pin reads **HIGH when the button is up and LOW when it is pressed** (`ASK_PIN_BUTTON` in `config.h`; `button` in the serial monitor shows which it reads).

**In plain words.** The locket is always in one of these states, and the button means something different in each:

| The locket is… | You press the button | What happens |
| --- | --- | --- |
| **READY** (`IDLE`) | once | It checks it can record (paired, card in and not full, buffers available), then **starts recording**. If something is missing it says what, stays not-recording, and the next press tries again |
| **RECORDING** | once | It **stops** the microphone and moves to *saving* |
| **SAVING** (`FINALIZING`: writing the last audio, fixing the file's header, checking it, queuing it) | any number of times | **Nothing.** Presses are noticed, logged as ignored, and thrown away. They can neither start nor stop a recording. Saving takes about a second |
| *(back to)* **READY** | once | A **brand-new** recording with a new id. The one before is untouched |

```text
        press                      press                     (automatic: about a second)
  READY ───────► RECORDING ───────────────► SAVING ─────────────────────────► READY
    ▲  start refused │ (an error is shown;                                       │
    │  press tries   ▼  press tries again)                  uploading happens    │
    └────────────── ERROR ◄────────────────────────────  on its own, afterwards ─┘
```

*Uploading is not a state of the button.* When saving ends, the finished file is **queued** on the card and the locket is READY straight away; a separate task uploads it whenever the network allows, and the website transcribes it later. You never wait for an upload or a transcript before the next recording.

What counts as "a press": the pin settling LOW for 50 ms after having been HIGH. So **contact bounce is one press**, **holding the button down is one press** (however long), **letting go is not a press**, and **a button already held down at power-up is not a press** (let go, then press). Nothing records on its own at power-up. Recording starts the moment the press is recognised, even if you keep holding the button.

What you see on the serial monitor (115200 baud), in order:

```text
[STATE] IDLE                      ready
[STATE] RECORDING                 first press: recording really started
[BUTTON] press: stop              second press
[STATE] FINALIZING                the microphone is off; the last audio is being saved
[EVENT] RECORDING_STOPPED seconds=12.31 bytes=393920
[EVENT] UPLOAD_QUEUED part=1 bytes=393920 file=r….wav      the file is complete, checked and waiting
[STATE] IDLE                      ready for the next press
[EVENT] UPLOADING file=r….wav     (any time later, on its own)
[EVENT] UPLOADED file=r….wav recording=<id> duplicate=0 (stored by the server)
```

These rules live in one table, `rec_step` in `core.cpp`, which every press goes through, and which is tested for every state and event and with 200,000 random events.

## What the locket sends and expects

Base URL: whatever you set with `server https://…` (HTTPS only unless built with `ASK_ALLOW_PLAIN_HTTP=1`). Authentication: a per-device credential, `Authorization: Bearer <device id>.<secret>`, issued once by pairing. The locket never sends a company or user id; the server derives them from the credential.

| Call | Request | Success |
| --- | --- | --- |
| Pair | `POST /api/device/v1/pair`, JSON `{"code":"ABCDE-FGHIJ","firmwareVersion":"0.2.0-web-upload"}` | `200` `{"deviceId","credential","config":{"heartbeatIntervalSeconds","maxUploadBytes","maxClipSeconds",…}}` |
| Heartbeat (every `heartbeatIntervalSeconds`, 30 by default, also while recording) | `POST /api/device/v1/heartbeat`, JSON `{"firmwareVersion","uploadQueueDepth","batteryPercent"?}` | `200` `{"serverTime","config"}` |
| Upload a part | `PUT /api/device/v1/recordings/{clipId}`, body = the raw WAV (streamed from the card, never held in RAM). Headers: `Authorization`, `Content-Type: audio/wav`, `Content-Length`, `X-Content-SHA256` (hex), `X-Recorded-At` (UTC, `2026-01-01T00:00:00Z`), `X-Session-Ref`, `X-Sequence` (1, 2, 3 …) | `201` stored, or `200` already stored, with the receipt `{"recordingId","clientRecordingId","status":"stored","sha256","bytes","durationMs","duplicate","startedAt"}` |

**A part is deleted only after the receipt has been checked**: `status` is `stored`, `clientRecordingId` is this part, `recordingId` is a UUID, and `sha256` and `bytes` equal what was sent. A bare `200` (a captive portal, a proxy) deletes nothing. Everything else, by status:

| Answer | The locket |
| --- | --- |
| `201` / `200` with a valid receipt | Deletes its copy |
| `200` / `201` without a valid receipt, or a reply too large, chunked or unreadable | **Keeps the file and tries again** |
| `409 recording_conflict` | Gives the part a new id and sends it again |
| `422 checksum_mismatch` | Keeps it, retries |
| `422`/`413` for audio the server will never take, `415` | Moves it to `/rejected`, does not retry |
| `401` | Stops uploading, keeps every file, asks again every 5 minutes, refuses to *start* recordings until paired again |
| `403` (not sent by the ASK server; a gateway) | Keeps the file, retries only every 5 minutes |
| `408`, `429`, `5xx`, no answer | Keeps the file; exponential back-off with jitter from 2 s to 5 minutes; honours `Retry-After` up to an hour |

Before sending, the locket checks that the file really is a WAV of the right format and size; a damaged one goes to `/rejected` without being sent.

## Set up, build and flash (Windows)

### Hardware

| Part | Notes |
| --- | --- |
| XIAO ESP32S3 **Sense**, expansion board attached | Microphone on GPIO 42 (clock) / 41 (data); card slot on SPI (SCK 7, MISO 8, MOSI 9) with chip select GPIO 21. **Check against your board revision's schematic**; the pins are in `config.h` |
| Push button | Between **D1 (GPIO2)** and GND. No resistor needed (the internal pull-up is used) |
| microSD, FAT32, 32 GB or smaller | About 2 MB per minute of audio waiting to be sent. Recording refuses to start below 8 MB free |
| Battery (optional) | No gauge on the board. Wire a divider to an analogue pin, set `ASK_PIN_BATTERY_ADC` (never GPIO2, the button) and the ratio |

**GPIO21 is both the card's chip select and the board's user LED.** Do not drive that LED. This firmware has no indicator of its own: use the serial monitor or the maintenance page.

### Arduino IDE 2

1. Install the Arduino IDE 2. In *File → Preferences → Additional boards manager URLs* add `https://raw.githubusercontent.com/espressif/arduino-esp32/gh-pages/package_esp32_index.json`.
2. *Tools → Board → Boards Manager*, install **esp32 by Espressif Systems**, version **3.3.x** (built with 3.3.12; the sketch uses `ESP_I2S.h`, which only the 3.x core has).
3. Open `platform\firmware\locket_web_upload\locket_web_upload.ino`.
4. *Tools*: **Board: XIAO_ESP32S3**, **PSRAM: OPI PSRAM** (**required**: the audio ring lives in PSRAM and the sketch refuses to record without it), **USB CDC On Boot: Enabled** (the board's default), **Partition Scheme: Default with spiffs (3MB APP/1.5MB SPIFFS)** (the default).
5. Select the port (*Tools → Port*; a charge-only cable shows none) and **Upload**.
6. *Tools → Serial Monitor*, **115200 baud**, line ending *Newline* (or *Both NL & CR*).

### Arduino CLI

```powershell
arduino-cli core update-index
arduino-cli core install esp32:esp32@3.3.12
arduino-cli compile --fqbn "esp32:esp32:XIAO_ESP32S3:PSRAM=opi" --warnings all platform\firmware\locket_web_upload
arduino-cli board list                                   # find the port, for example COM5
arduino-cli upload  --fqbn "esp32:esp32:XIAO_ESP32S3:PSRAM=opi" -p COM5 platform\firmware\locket_web_upload
arduino-cli monitor -p COM5 -c baudrate=115200
```

### Configure it

**Wi-Fi needs no command.** A test network is built into `config.h` (`ASK_DEFAULT_WIFI_SSID` `ESPTEST`, `ASK_DEFAULT_WIFI_PASSWORD` `12345678`: a throwaway phone or laptop hotspot made for testing, see [How Wi-Fi works](#how-wi-fi-works)). Switch that hotspot on (2.4 GHz, WPA2, name and password exactly as above), power the locket, and it joins by itself. Then, in the serial monitor:

```text
server https://ask.example.com
pair ABCDE-FGHIJ
status
```

To use a different network without editing the source, type `wifi "My Network" my-wifi-password` once. The server address and the pairing credential are still set over serial, never in the source.

| Command | What it does |
| --- | --- |
| `wifi <name> <password>` | Joins this network instead of the built-in one, and remembers it until `wifi default` or a new firmware is flashed (the password is never echoed or printed). 2.4 GHz only |
| `wifi default` | Goes back to the built-in network |
| `server <https://address>` | The ASK server. `http://` is refused unless the firmware was built with `ASK_ALLOW_PLAIN_HTTP=1` |
| `pair <CODE>` | Redeems the one-time code from the website (below) and stores the credential |
| `status` | State, microphone, card, Wi-Fi, server, clock, queue counts, last problem. No secrets |
| `button` | Shows whether the button reads up (HIGH) or down (LOW) right now: for checking the wiring |
| `record` | The same as one press of the button (starts, or stops, or is ignored while saving) |
| `retry` | Skip the wait and try uploading now |
| `live on`, `live off` | The status line below. On by default |
| `files` | Lists the recordings on the card and which can be sent (not while recording) |
| `unpair` | Forgets the credential. Files on the card are kept and are sent after the next pairing |
| `ap`, `ap on`, `ap off`, `ap password <12-63 chars>` | The local maintenance Wi-Fi (below). `on`/`off` restart the locket, and refuse while recording |
| `reboot` | Restarts (refused while recording) |

**Certificates.** For HTTPS the locket checks the server's certificate against a certificate authority you put on the card as **`/ca.pem`** (PEM, the authority that signed the server's certificate: for a public certificate the root such as ISRG Root X1, for your own authority its certificate). Without that file the locket sends nothing and says so (`last problem`). `ASK_INSECURE_TLS=1` switches checking off and exists for development only; both it and `ASK_ALLOW_PLAIN_HTTP=1` print a warning at every start.

### The status line, and what it prints when you press the button

Every 10 seconds the monitor prints one line, so you can always tell whether it is recording, online or sending, without waiting for an event:

```text
[STATUS] READY - PRESS BUTTON | Wi-Fi: ESPTEST -54 dBm | server: online | button: up | to send 0 | untimed 0 | uploaded 3 | upload: idle
[STATUS] RECORDING 23 s (part 1) | Wi-Fi: ESPTEST -54 dBm | server: online | button: up | to send 0 | untimed 0 | uploaded 3 | upload: idle
[STATUS] READY - PRESS BUTTON | Wi-Fi: ESPTEST -54 dBm | server: online | button: up | to send 1 | untimed 0 | uploaded 3 | upload: SENDING a part now
```

* **State**: `READY - PRESS BUTTON`, `RECORDING <seconds> (part N)`, `FINALIZING` (saving the last part to the card) or `ERROR`.
* **Wi-Fi**: the network and signal strength, or `NOT connected (retrying)`.
* **server**: `online` (the last heartbeat was accepted), `not reachable`, `not paired`, or `REFUSED, pair again`.
* **button**: what the board reads on its button pins right now, `up` or `DOWN`. Two buttons count: a push button wired between **D1 and GND**, and the board's own small **BOOT** button (set `ASK_PIN_BUTTON_ALT` to -1 in `config.h` to turn that one off). The RESET button is not a record button.
* **to send**: recordings in `/pending` waiting to be uploaded. **untimed**: recordings in `/untimed`, kept but never sent by themselves (recorded before the locket had a clock). **UNREADABLE n** (only shown when there are some): files in `/pending` that this firmware did not name and cannot send, such as clips left by the other (continuous-clip) sketch. They are kept and are not counted as waiting.
* **uploaded**: parts the server has confirmed since the locket started.
* **upload**: `SENDING a part now` while one is on its way.

What it prints when something happens:

```text
[BUTTON] D1 button (GPIO2): DOWN                                         <- the board saw a button go down ...
[BUTTON] D1 button (GPIO2): released                                     <- ... and come up (the BOOT button says the same, as GPIO0)
[BUTTON] press noticed (READY - PRESS BUTTON): starting a recording      <- every press it acts on, and what it did
[STATE] RECORDING                                                        <- it really is recording now
[BUTTON] press: stop                                                     <- the second press
[EVENT] RECORDING_STOPPED seconds=12.31 bytes=393920
[EVENT] UPLOADING file=r….wav
[EVENT] UPLOADED file=r….wav recording=<id> (stored by the server)
[UPLOAD] r….wav was not sent: upload could not reach the server. Trying again in 12 s (type retry to try now).
```

If you press a button and **no** `[BUTTON] … DOWN` line appears at all, the board is not seeing that button electrically (a loose wire, the wrong pin, or a different button): that is a wiring problem, not software. With no button wired you can still press the board's BOOT button, or type `record` in the monitor, which does exactly what one press does.

Type `files` to list what is on the card (`/pending`, `/untimed`, `/rejected`, `/recording`) and which files can be sent. A file whose name this firmware did not make, such as a recording left by the other (continuous-clip) sketch, is marked `NOT a name this firmware makes`: it is ignored and never sent, and the monitor says so once (`… have names this firmware does not recognise`). Type `live off` to silence the status line and `live on` to bring it back. The board has no light of its own to show any of this: its only user LED shares a pin with the memory card, so the serial monitor is the display.

### How Wi-Fi works

The Wi-Fi manager (`wifi_manager.cpp`) is its own task. It starts in `setup()` before anything else is ready, so it never delays the button, the microphone or the card, and the locket records whether or not it is connected.

* **Which network.** The built-in one (`ESPTEST`) unless `wifi <name> <password>` was typed on **this** firmware build. A network saved by an older build, or typed on an earlier build, is **cleared** at the first start of a new build (`[WiFi] A network saved before this firmware was flashed was cleared; using the built-in network.`), so a forgotten test setting can never override the one in `config.h`. Each compile has its own stamp (its date and time, mixed with the built-in name and password): flashing again, or editing the built-in network, starts afresh. `status` says `(built-in network)` or `(network you typed)`.
* **No pairing needed.** The locket joins before it is paired, because pairing itself needs the network.
* **Trying and trying again.** One try waits up to 20 s. If it fails it says why and waits a random time of up to 5 s, then up to 10 s, 20 s, 40 s, and up to 60 s from then on (never less than half of the limit), before the next try. A link that drops is noticed within a second and rejoined the same way. `wifi …` or `wifi default` makes it try the new network at once.
* **Why it failed.** Printed from the reason the chip reports, in words, with the chip's own name and code:

  | The chip says | The locket prints |
  | --- | --- |
  | `NO_AP_FOUND` (201) | no network with that name was found: is the hotspot on, in range, and 2.4 GHz? |
  | `AUTH_FAIL` (202), `4WAY_HANDSHAKE_TIMEOUT` (15), `HANDSHAKE_TIMEOUT` (204) | the password was not accepted: is it right for that network? |
  | `ASSOC_FAIL` (203), `CONNECTION_FAIL` (205) | the access point refused the connection |
  | `BEACON_TIMEOUT` (200) | lost contact with the access point: out of range? |
  | nothing within 20 s | no answer within the time allowed |

* **What you see** at a normal start (the password is never printed, here or anywhere):

  ```text
  [WiFi] Connecting to ESPTEST...
  [WiFi] Connected successfully
  [WiFi] IP address: 192.168.43.57   signal strength (RSSI): -52 dBm
  ```

  and when the hotspot is off:

  ```text
  [WiFi] Connecting to ESPTEST...
  [WiFi] Connection failed: no network with that name was found: is the hotspot on, in range, and 2.4 GHz? (NO_AP_FOUND, code 201). Trying again in 4 s.
  [WiFi] Connecting to ESPTEST... (attempt 2)
  ```

  `status` and the maintenance page show the same, plus the last reason until a connection succeeds.
* **Recording without Wi-Fi.** Everything is recorded to the card and queued (`UPLOAD_QUEUED`); nothing is reported as uploaded until the server's receipt has been checked, and the queue is sent after the network returns. One thing to know: a recording made before the clock has ever been set (the clock comes from the network) is timed exactly if the network arrives in the same power-on; if the locket is restarted first, that file is kept in `/untimed` and is not sent automatically.
* **The built-in password is in the source.** `config.h` holds `ESPTEST` / `12345678` in plain text, and so does the compiled firmware (anyone with the chip or the `.bin` can read it). That is acceptable for a throwaway test hotspot only. Do not put a real network's password there; use `wifi …` for that, or empty both settings (`""`) for a build with no built-in network. See [../../docs/SECURITY.md](../../docs/SECURITY.md).

### Pair it and see a recording on the website

1. Sign in as a manager. **Devices → Pair a locket**, name it, choose **Create pairing code**, and note the code (it works once and expires).
2. In the serial monitor: `pair <code>`. It answers `OK: paired as <device id>`. The locket appears **online** in the dashboard within one heartbeat (30 s), from its authenticated heartbeats.
3. Press the button, speak for a few seconds, press it again. The serial monitor shows `[STATE] RECORDING`, `RECORDING_STOPPED`, `UPLOAD_QUEUED`, `[STATE] IDLE`, and then `UPLOADED … (stored by the server)`.
4. **Recordings** in the website shows it with its processing state. **A processing worker must be running** (`python -m app.worker`, with `ASK_AI_PROVIDER=stub` for development, which writes clearly labelled placeholder text, or `local` for real transcription) or the recording stays *queued*. See [../../docs/AI.md](../../docs/AI.md). A transcript is never faked.

### A ten-minute physical test (on the real board)

**Nothing below has been done yet: it is what to do on the day you have the board.** Write down what you see.

1. **Wiring.** Open the serial monitor. Type `button` with the button up: it must say `up (reads HIGH)`. Hold the button and type `button`: `DOWN (reads LOW)`. If it says DOWN with nothing pressed, or never says DOWN, check the D1 and GND legs.
2. **Ready, not recording.** Reset the board. It must reach `[STATE] IDLE` and `[READY]` and **not** start recording by itself. Reset it again while holding the button: it must say `held down at power-up` and not record until you let go and press again.
3. **Wi-Fi, then pair.** Switch the `ESPTEST` hotspot on (2.4 GHz, password `12345678`) and power the locket: within about 20 s the monitor says `[WiFi] Connected successfully` with an IP address and signal strength, with no `wifi` command typed. Then `server …`, `pair …` as above, and `status`: paired, Wi-Fi connected, card ready, microphone ok. Also try: hotspot off at power-on (`Connection failed … NO_AP_FOUND`, then it joins within a minute of switching it on), and a record/stop while it is still failing (the recording is queued and nothing says uploaded).
4. **One recording.** Press once and let go: `[STATE] RECORDING`. Count to ten out loud, near the locket. Press once more: `[STATE] FINALIZING`, `RECORDING_STOPPED`, `UPLOAD_QUEUED`, `[STATE] IDLE`. Within a minute: `UPLOADED … (stored by the server)`.
5. **Hold and mash.** Start a recording, press and hold the button for five seconds: it must stop once and **not** start again. Press it five times fast right after a stop: you should see `press ignored while FINALIZING` or a clean new start, never two recordings at once.
6. **The website.** The recording is in your company's list within a minute, state *queued* then (once a worker is running) *transcribing…* and *completed*. If the worker uses the development stub, the transcript is labelled placeholder text.
7. **Offline.** Switch the Wi-Fi router off, record ten seconds, switch it on. `UPLOAD_QUEUED` appeared at once; `UPLOADED` appears after the network returns; the website shows it once, not twice.
8. **Listen.** Take the card out after step 4 (before the upload deletes the file; set `ap`/`retry` aside or switch the network off) and play the WAV on a computer: it is your voice, at a sensible level, with no gaps.

For the full list, with expected results, see `HW-70` to `HW-7S` in [../../docs/HARDWARE_ACCEPTANCE_TESTS.md](../../docs/HARDWARE_ACCEPTANCE_TESTS.md).

## The local maintenance page

Off unless you type `ap on`. Then the locket makes its own Wi-Fi network (name `ASK-LOCKET-XXXX`, password chosen by the locket on first use, 16 characters; type `ap` on the **USB serial connection** to see it, and `ap password …` to set your own, 12 characters or more). Join it and open `http://192.168.4.1/`.

It shows state, microphone and card health (free space, write retries, remounts, **audio lost across a remount**), Wi-Fi, whether the server is reachable, the upload queue, the last upload and the last problem, with the firmware version. It answers only on that network (a request arriving by way of the Wi-Fi the locket uses for the internet gets `403`), shows no transcript, credential or password, and does not name any service. It is a maintenance tool, separate from the company website. `ASK_DASHBOARD_AUDIO_DOWNLOAD=1` (off) would let someone on that network download queued recordings; recordings are personal data, so it is for support builds only.

## `config.h` safety settings

| Setting | Default | Why |
| --- | --- | --- |
| `ASK_ALLOW_PLAIN_HTTP` | `0` | Plain `http://` sends the credential and the audio in the clear. Local development only |
| `ASK_INSECURE_TLS` | `0` | `1` stops checking the server's certificate. Development only, never a deployed locket |
| `ASK_DEFAULT_WIFI_SSID`, `ASK_DEFAULT_WIFI_PASSWORD` | `ESPTEST`, `12345678` | The network joined at every start, with no serial command. **Plain text in the source and the binary**: a throwaway test hotspot only. Name 1–32 characters; password 8–63 (or empty for an open network); both empty for no built-in network. A bad value is reported at start and ignored |
| `ASK_UPLOAD_WHILE_RECORDING` | `1` | Send finished parts during a long recording. `0` waits until you stop |
| `ASK_DASHBOARD_AUDIO_DOWNLOAD` | `0` | See above |
| `kAudioGain` | `1.0` | The original recorder used 1x because 4x clipped |
| `kDefaultSegmentSeconds` | `300` | Part length. Must be at most the server's clip limit (600 s by default); the server's value, learned at pairing, lowers it further |
| `kMaxSessionSeconds` | `7000` | A safety stop (the original's limit) |
| `kMinFreeBytes` | 8 MB | Recording refuses to start, and stops, when the card has less room than this |

## What was and was not checked

**Done on this computer** (everything under `platform/firmware/tests` and `platform/api/tests/test_firmware_*`):

* **Real toolchain build.** Arduino CLI with `esp32:esp32` 3.3.12 compiles and links the sketch for `XIAO_ESP32S3` (PSRAM: OPI) with `--warnings all`: see [../../docs/WEB_UPLOAD_FIRMWARE.md](../../docs/WEB_UPLOAD_FIRMWARE.md) for the sizes and the exact result. Compiled is not flashed.
* **Unit tests of the rules** (`core.cpp`, C++11, `-Wall -Wextra -Werror -pedantic`): the shared half is run by the same 3,815 checks as the continuous-clip firmware; the new half (part names, WAV check, receipt check, debounce, planning, the recording state machine, and the Wi-Fi rules: reasons in words, which reasons end a try, which network names and passwords are valid) has 61,239 more, including a check of the state machine against 200,000 random events.
* **The firmware's own sources run against simulated hardware** (`tests/hostsim`): the sketch's real `setup()`, capture task, card writer, uploader, dashboard and console, with a simulated button (GPIO2, pulled up), card, microphone, Wi-Fi, HTTP client and RTOS. 76 scenarios: joining the built-in Wi-Fi network by itself (with a slow, wrong-password, absent, dropped and reappearing network, a network typed over it, a stale saved network, no built-in network, and recording meanwhile), the two-press button cycle (power-on idle, a button held at power-up, hold, bounce, presses while saving), multi-part recordings with the audio checked sample by sample, card write failures and remounts (with and without lost data), a card that disappears, a power cut, a full card, an unreachable or hanging server, 5xx, 401, 403, 413, 422, lost replies, repeats, id conflicts, replies that are not receipts, a damaged file on the card, a missing certificate file, an unset clock, pairing, the maintenance page and the console. The simulator also counts two tasks using the card at once, stale file handles and too many open files: all zero. Each safeguard was broken on purpose to confirm a test notices (see the report).
* **The firmware's upload code against the real API**: the same code, with its HTTP client wired to a real uvicorn server and database (5 tests): pairing, headers, streaming, hash, receipts, repeats (`200 duplicate`), a revoked locket, company isolation between two companies' lockets, and a transcription that fails (the audio is untouched, the real status is shown, the next recording uploads).

**Not done, so not known to work** (all need a board):

* Anything on the board: the microphone's real level, the card's real behaviour (speed, a pull-out, a power cut), the pins, **TLS on the chip with a real certificate** and its memory use, the radio, task stack sizes, heap over hours, power use.
* **Timing under the real clock.** The simulator runs faster than real time; it proves ordering and recovery logic, not that the writer keeps up with the microphone on a real card at 4 MHz.
* Uploading while recording on real hardware (the back-pressure rule is tested in simulation only).
* Over-the-air updates, deep sleep, a hardware watchdog, an indicator LED: none implemented.

## Known limits

* The clock is set over the network at each start-up (the chip has no battery-backed clock). A locket that records before it has ever reached the network is timed exactly if the network arrives in the same start-up; otherwise those parts wait in `/untimed`.
* A recording is cut up on whole 32 KB blocks, so parts are 299 s, not 300 s.
* A part boundary falls wherever the block does, possibly mid-sentence. The server processes each part separately, so a speaker label ("Speaker 1") is not tied across parts.
* The Wi-Fi password (built-in, in the firmware image; or typed, in the chip's storage) and the pairing credential are stored unencrypted; enabling flash encryption is the way to change that and is not done here.
* Making sure the people recorded know and agree is the company's responsibility.
