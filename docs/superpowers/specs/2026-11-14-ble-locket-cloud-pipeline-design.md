# ASK locket: Bluetooth to the phone, cloud transcription and summary, Wi-Fi only for updates

Status: approved by the owner on 2026-11-14 ("go ahead"). Written from the owner's and Nandu's brief.

## 1. Intent

The ASK locket is worn in meetings. It must be simple for one person to set up and use:

1. Turn the locket on. It shows up in the ASK phone app as **ASK-XXXXXX** (its product ID).
2. Tap it. A pairing box asks for a code. The code arrives **by email**. Enter it, and the locket and phone are paired.
3. During a meeting, the locket sends the voice to the phone over **Bluetooth**. That is the locket's only daily job.
4. The phone sends the audio to the ASK server. The server gets it transcribed by **Google Cloud Speech-to-Text**, then summarised by **Gemini**.
5. The phone keeps a local backup: `transcription.txt` and `summary.txt` (plus the audio).
6. **Wi-Fi is used only to install firmware updates over the air (OTA).** Nobody plugs in a USB cable.

## 2. Goals, non-goals, anti-goals

Goals
- Every locket has a **product ID fixed at manufacture**. Once set it can never be changed, on the locket or on the server.
- **One person per locket by default.** Only an **administrator** can raise a locket's limit.
- Pairing needs a **one-time code emailed to the user**, so having the locket in hand is not enough.
- Audio reaches the phone reliably: if the phone walks away mid-meeting, the locket keeps recording to its card and the phone catches up when it is back.
- Every button in the app does something real. Screens with no real data behind them are removed.

Non-goals (for this round)
- Speaker recognition by voice print (the old SpeechBrain path). Google's speaker labels ("Speaker 1", "Speaker 2") are used instead.
- Classic Bluetooth audio (headset profiles). The board supports Bluetooth Low Energy only.
- Updating firmware over Bluetooth. Wi-Fi only, as requested. Can be added later as a fallback.

Anti-goals (failure even if it "works")
- Google or Gemini keys inside the phone app (they can be extracted). Keys stay on the server.
- A wrong person getting onto a locket because the code was guessable or reusable.
- A locket that bricks after a bad update.
- Showing invented data as if it were real.

## 3. Constraints found in the code and on this machine

- Board: XIAO ESP32-S3 Sense. Bluetooth LE 5 only; **one 2.4 GHz radio shared** by Bluetooth and Wi-Fi.
- iPhones never list custom Bluetooth LE devices in Settings, and Android does so inconsistently. **Discovery and pairing start from the ASK app's device list**; the operating system's pairing box then asks for the code.
- Bluetooth from a web page does not work on iPhone at all. The web build of the app cannot talk to a locket; those buttons are hidden on web, not shown disabled.
- This machine has no C++ compiler, ESP32 toolchain, phone build or Docker. Firmware is written but not compiled here; the phone's Bluetooth code needs a development build on a phone. Google and Gemini run only after the owner puts keys in `platform/api/.env`.

## 4. Approaches considered

1. **Phone processes on its own and syncs results.** Rejected after the owner's brief: they want Google and Gemini, and keys must not live on the phone.
2. **Phone calls Google and Gemini directly.** Rejected: puts paid API keys in the app.
3. **Phone relays audio to the ASK server, which calls Google and Gemini and returns the two text files (chosen).** Keys stay on the server, the server keeps a synced copy (the owner chose "phone syncs to server"), and the phone keeps its own `.txt` backup.

For pairing:
- A fixed PIN printed on the locket: rejected, anyone holding the locket can pair.
- **Code derived from a per-locket secret and a fresh number from the locket, emailed by the server (chosen).** The locket can check the code with no internet.

## 5. Design

### 5.1 Product ID and locket secret

- Product ID: `ASK-` plus 6 characters (the existing `devices.public_id` format). Generated by the server when an administrator registers a locket.
- Locket secret: `HMAC-SHA256(ASK_LOCKET_MASTER_KEY, product_id)`, 32 bytes. The server never stores it; it recomputes it. `ASK_LOCKET_MASTER_KEY` is a new server setting (separate from `ASK_SECRET_KEY`, at least 32 characters, never logged).
- Factory provisioning: `python -m app.cli register-locket` (or the admin screen) creates the locket and prints the product ID and secret once. The secret is written to the locket over USB serial with `provision <productId> <secretHex>`. The firmware stores both in flash and **refuses any later `provision`** (write-once). On the server a database trigger refuses any change to `public_id`.

### 5.2 Pairing with an emailed code

```
App                     Locket                      Server
 | scan, sees ASK-7KQ2MX  |                           |
 | read PAIR_NONCE ------>| 16 random bytes           |
 | POST /api/lockets/ASK-7KQ2MX/pairing-code {nonce} ->| checks: signed in, locket registered,
 |                        |                           |   user already on it OR people < limit
 |                        |                           | code = 6 digits from HMAC(secret, "ASK-PAIR"+nonce)
 |                        |                           | emails code to the user; returns masked address
 | bond (LE Secure Connections, passkey entry) ->      |
 |   OS box: "Enter code" | locket's passkey = same code
 | user types code ------>| match -> bonded           |
 | read BOND_PROOF ------>| HMAC(secret,"ASK-BONDED"+nonce), encrypted read only
 | POST /api/lockets/ASK-7KQ2MX/paired {nonce, proof} ->| checks proof, adds user (respects limit)
```

- Code: `uint32_be(HMAC-SHA256(secret, "ASK-PAIR" || nonce)[0..4]) mod 1_000_000`, zero-padded to 6 digits. Same formula in firmware and server (tested against shared vectors).
- The locket makes a new nonce at boot, after every pairing attempt (right or wrong), and every 10 minutes. One guess per nonce, at most 5 attempts per 10 minutes.
- The server rate-limits code requests per user and per locket (both counted before the locket is looked up), records each in the audit log, and keeps a pending request for 10 minutes. `paired` only succeeds with a pending request for the same nonce **and** the locket's bonding proof: after bonding, the locket exposes `HMAC-SHA256(secret, "ASK-BONDED" + nonce)` (64 hex) on an encrypted, authenticated-only characteristic, and the server recomputes it. Without it, someone could ask for a code with a made-up nonce and join a locket they never held (found in the final review). Only lockets registered as Bluetooth (`devices.transport = 'bluetooth'`) can be paired this way.
- **People-per-locket limit**: `devices.max_users`, default 1. A code is only issued if the user is already on the locket or the locket has fewer people than its limit. Only an administrator can change the limit (`PATCH /api/lockets/{id}/limit`), and never below the current number of people.
- Removing a person (administrator, or the person themselves with "Forget this locket") frees a place. The locket's bond list is cleared from the app with a `FORGET` command when possible.

### 5.3 Bluetooth service (locket is the server, phone is the client)

Service `69bc378a-a795-4f0c-984d-e2cee6c5ea54`. Advertised name = product ID.

| Characteristic | UUID | Access | Content |
| --- | --- | --- | --- |
| INFO | `8242cd7a-098d-4b2d-9335-b9f4df3b7087` | read, open | `ASKINFO/1 <productId> <firmwareVersion> <batteryPct> <bonded:0/1>` |
| PAIR_NONCE | `30e12be5-e356-4896-aa4b-c78acd1cb186` | read, open | 16 bytes |
| CONTROL | `a4e0d5f7-39b8-4614-a440-5398719e89f1` | write, encrypted + authenticated | text command, one per write (below) |
| BOND_PROOF | `7bac8620-f67c-4bd2-ac89-b6fcc04ebad7` | read, encrypted + authenticated | 64 hex: `HMAC-SHA256(secret, "ASK-BONDED" + nonce)` for the nonce this bond used |
| STATUS | `72666507-9e9a-40fb-a060-dda51aa64f35` | notify, encrypted | `ASKSTAT/1 <state> <batteryPct> <sessionId> <lastSeq> <otaPct>` |
| AUDIO | `3b73557c-0f90-4af2-9416-10b0c91aaf96` | notify, encrypted | one binary frame per notification (format below) |

- Frames use the binary format already in the app (`platform/web/src/domain/device/framing.ts`): a 42-byte header `"AS"`, version 1, type (`0x02` START, `0x03` AUDIO, `0x04` END), flags, header length 42, session ID (16 ASCII), sequence (uint32 big-endian), timestamp ms (uint64 big-endian), payload length (uint32 big-endian), CRC-32 (IEEE, over header bytes 0..37 plus the payload), then the payload. START is sequence 0, AUDIO frames 1, 2, 3 ..., END follows the last AUDIO frame. (This replaces the text `ASK/1` header described in `docs/DEVICE_PROTOCOL.md`, which costs too many bytes per Bluetooth packet.)
- Audio: 16 kHz mono, compressed on the locket with **IMA ADPCM** (4:1, 64 kbps). Each AUDIO payload is 132 bytes: a 4-byte block header (`predictor` int16 little-endian, `stepIndex` uint8, one reserved zero byte) then 128 bytes of nibbles, low nibble first, = 256 samples (16 ms). Every block carries its own starting state, so a resent frame decodes on its own. A frame is 174 bytes; the phone asks for an MTU of 185. The phone decodes to 16-bit PCM and uploads WAV (Google needs `LINEAR16`).
- The locket writes every frame to the card first, then sends.
- CONTROL commands: `REC START`, `REC STOP`, `ACK <sessionId> <seq>` (phone has everything up to seq), `RESEND <sessionId> <fromSeq>`, `TIME <unixMs>`, `WIFI <ssidHex> <passwordHex>`, `WIFI CLEAR`, `OTA <version> <sizeBytes> <sha256Hex> <urlHex>`, `FORGET`.
- On reconnect the phone reads STATUS and sends `RESEND` from its last acknowledged frame; the locket deletes a session from the card once `ACK` covers its `SE` frame.

### 5.4 Phone to server

- Signed-in user (existing cookie session). For the native app, `login` and `me` also return `csrfToken` in the body, because native code cannot read cookies.
- `PUT /api/lockets/{productId}/recordings/{clientRecordingId}` with the WAV body, `X-Content-SHA256`, `X-Recorded-At`. The user must be on that locket. Idempotent like the existing device upload. The recording is visible to the people on the locket at the time it arrives (generalises today's wearer rule).
- The worker runs the new `google` provider:
  - Speech-to-text: Google Cloud Speech-to-Text v1 `recognize`, `LINEAR16`, 16 kHz, automatic punctuation, speaker diarization on. Audio is sent in chunks of up to 55 s (the synchronous limit is 1 minute) and the results are joined with offsets.
  - Summary: Gemini (`google-genai`), model from `ASK_GEMINI_MODEL`. A fixed prompt asks for a plain-text summary with Summary, Decisions, Action items and Open questions, using only what the transcript says. Requests to Google and Gemini have time limits (120 s and 60 s).
- `GET /api/recordings/{id}/transcription.txt` and `/summary.txt` return the files. Lines in `transcription.txt` look like `[00:01:05] Speaker 1: text`.
- Settings: `ASK_AI_PROVIDER=google`, `ASK_GOOGLE_APPLICATION_CREDENTIALS` (path to a service-account JSON), `ASK_GOOGLE_STT_LANGUAGE` (default `en-US`), `ASK_GEMINI_API_KEY`, `ASK_GEMINI_MODEL`. Missing keys make the worker refuse to start with a clear message, like today.

### 5.5 Firmware updates over Wi-Fi

- The operator uploads a build: `PUT /api/firmware/{version}` with the `.bin`; the server stores it and its SHA-256. Only administrators of the company named in `ASK_FIRMWARE_PUBLISHER_COMPANY_ID` may upload (every locket on the server is offered the build, so a customer must never publish it).
- `GET /api/firmware/latest` tells the app what is newest. If the locket's version is older, the app shows **Update firmware**.
- The app sends Wi-Fi details once (`WIFI ...`, over the encrypted Bluetooth link), then `OTA <version> <size> <sha256> <url>`. The URL carries a signed token valid for 30 minutes (`GET /api/firmware/{version}/download?token=...`), so the locket needs no account.
- The locket stops audio, turns on Wi-Fi, downloads over HTTPS into the spare app slot, checks size and SHA-256, switches slot and restarts. The new firmware marks itself good after Bluetooth comes back up; if it crashes first, the bootloader rolls back. Progress goes out on STATUS.
- The hard-coded test hotspot is removed from the new firmware; Wi-Fi details only arrive from the app.

### 5.6 App screens (Expo app in `platform/web`; the same code runs on the phone and as a website)

| Screen | Buttons and what they do |
| --- | --- |
| Sign in | Sign in (server), Forgot password (emails a reset link) |
| Today | Your locket card (battery, recording state; tap opens the locket), Start/Stop recording (sends `REC START/STOP`; phone only), latest recordings (open) |
| Recordings | List from the server with status (uploading, transcribing, summarising, ready, failed); tap opens |
| Recording | Transcript, Summary, Play audio, Save files (writes `transcription.txt` and `summary.txt` to the phone; downloads on web), Process again, Delete |
| Ask | Search across transcripts and summaries (server search); results open the recording |
| You | Your lockets, Team (administrator), Account (change password), Sign out |
| Lockets | Find and pair (phone only), each locket: product ID, firmware, battery, people on it, limit (administrator can raise), Wi-Fi for updates, Update firmware, Forget this locket |
| Team | Members and roles, Invite by email, Remove |

Removed: the demo "understand" runner, memory graph, agents, proactivity, the local follow-up demo, and the unreachable onboarding screens. The phone saves its backup under the app's documents folder: `ASK/<recordingId>/audio.wav`, `transcription.txt`, `summary.txt`.

## 6. Build order

1. Server: locket registry, write-once product ID, limit, emailed pairing codes, `csrfToken` in body, phone upload, visibility rule, `google` provider, text-file endpoints, firmware hosting. Tests for each.
2. App: API client and sign-in, screens above wired to the server, local backup files, Bluetooth layer behind an interface (real implementation with `react-native-ble-plx` on the phone, hidden on web).
3. Firmware: new sketch `platform/firmware/locket_ble` (recording to card, button, BLE service, pairing code, ADPCM, OTA), pairing-code test vectors shared with the server.
4. Docs, checks, launch on localhost.
